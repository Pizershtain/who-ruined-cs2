# M4.1 backend upload limits and Docker runtime

Date: 2026-10-25  
Scope: backend ingestion, worker runtime, local Docker Compose and operational
documentation. This is not full M4.

## Upload policy

The default `MAX_UPLOAD_BYTES` is `536870912` bytes (512 MiB). It is a finite
configuration value, validated as a positive safe integer with a maximum
supported configuration of 2 GiB. `MIN_UPLOAD_FREE_BYTES` defaults to
`268435456` bytes (256 MiB).

The value is based on a read-only audit of 116 locally available real demos:
the maximum was 427.279 MiB, p95 395.483 MiB, and 64 files exceeded the former
250 MiB limit. A 512 MiB cap covers the observed maximum with 84.721 MiB
(19.83%) headroom. No observed file exceeded 600 MiB. This is an upload policy,
not a guarantee that every accepted demo fits the worker's parser memory or
timeout budget.

## Bounded upload flow

1. An outer admission interceptor validates `Content-Length` when present and
   rejects a clearly oversized multipart body before a temporary file is
   opened. Missing or understated values are not trusted.
2. Free filesystem space is checked before transfer. The expected upload plus
   the configured reserve must fit.
3. Multer/Busboy streams to a random server-owned file under
   `DATA_DIR/uploads`. The exact file boundary is accepted; one byte over is
   rejected by the streaming counter.
4. Wrong extensions are rejected before writing. The service then verifies a
   non-empty Source 2 signature and parser header.
5. Hashing is streamed from disk. Match and job rows are committed in one
   transaction. A transaction failure removes only the newly owned temporary
   file. A concurrent unique-key winner is returned as a duplicate.
6. The abort-aware storage removes a partial file after a client disconnect.
   Final paths are generated by the server and canonicalized under `DATA_DIR`.

The complete demo is never buffered in the Node heap.

## HTTP errors

| HTTP | Code | Meaning |
|---:|---|---|
| 413 | `SIZE_LIMIT` | Streaming file limit or safe early body limit exceeded. |
| 415 | `INVALID_DEMO` | Uploaded filename is not `.dem`. |
| 422 | `INVALID_DEMO` | Missing, empty, malformed, truncated or unconfirmed Source 2 demo. |
| 503 | `INGESTION_PERSISTENCE_FAILED` | Match/job transaction could not be committed. |
| 507 | `STORAGE_UNAVAILABLE` | Upload storage is unavailable or lacks the safety reserve. |

Framework and unknown errors are normalized; filesystem paths, raw parser
messages and stack traces are not returned. Logs contain only aggregate byte
count, duration and duplicate status for accepted uploads.

## Environment

| Variable | Default | Notes |
|---|---:|---|
| `MAX_UPLOAD_BYTES` | `536870912` | Exact maximum file bytes. |
| `MIN_UPLOAD_FREE_BYTES` | `268435456` | Free space retained beyond expected upload. |
| `PARSE_TIMEOUT_MS` | `120000` | Positive integer, at most one hour. |
| `WORKER_POLL_MS` | `1000` | Positive integer, at most 60 seconds. |
| `LOCAL_DATA_DIR` | `./data` | Host directory mounted to `/data` by Compose. |
| `API_PORT` | `3000` | Published on host loopback only. |
| `API_BIND_HOST` | local `127.0.0.1`; container `0.0.0.0` | Compose supplies the container value explicitly. |

For an isolated Compose run, use a new empty host directory and unique project
name. A project name alone does not isolate a bind mount:

```powershell
$env:LOCAL_DATA_DIR = '<dedicated-empty-directory>'
$env:API_PORT = '3301'
docker compose -p wrc-isolated up --build api worker
```

The supplied Compose resource limits are 512 MiB / 1 CPU for API and 2 GiB /
2 CPUs for worker. The worker is the only native-parser process.

## Verification and known limits

A real 262.806 MiB demo passed local HTTP upload, worker processing, automatic
participation-sidecar creation, H2/H1/H2 retrieval and legacy endpoints in an
isolated database/data directory. The API working-set before/after delta during
that transfer was 0.453 MiB; this is an observation, not a formal peak-memory
proof. The worker peak working set observed during parsing was 447.203 MiB.

The same demo also passed an actual isolated Docker Compose `up --build` run.
The API was published only on host loopback and was healthy; API and worker
shared one dedicated bind mount rather than the normal project data directory.
HTTP upload returned 202, the worker completed, and the prepared participation
sidecar existed before the first rating GET. H2 default equalled explicit H2,
H1 remained independently selectable, and repeated GETs left the sidecar
unchanged. SQLite, reports and the sidecar remained readable after restarting
both containers. Recreating the isolated services with the participation flag
off returned 404 `EXPERIMENTAL_PARTICIPATION_RATING_DISABLED`; restoring the
flag restored the same result without reparsing.

The Docker images install OpenSSL explicitly. Repository files copied into the
runtime image belong to the unprivileged `node` user, and API startup runs
`prisma db push --skip-generate`; this avoids runtime client regeneration and
the permission warning found during the first container start.

Exact boundary, boundary +1, missing/forged length, chunked upload, wrong
extension, empty/truncated input, client abort, storage failure, transaction
failure and concurrent dedup are covered by automated or real HTTP checks.

The native parser call is synchronous. `PARSE_TIMEOUT_MS` is validated and a
call that returns after the deadline becomes `PARSE_TIMEOUT`, but the current
worker cannot forcibly interrupt a native call that never returns. Hard parser
process isolation belongs to later M4 work.

The experimental participation endpoint remains default-off. H2/H1 IDs,
digests, formula, award policy, sidecar schema and GET read-only behavior are
unchanged.
