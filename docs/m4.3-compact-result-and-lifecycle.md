# M4.3 compact result, policy and lifecycle

M4.3 keeps SQLite as the accounting index and exactly one durable gzip JSON
result per completed new match. The stored schema is `match-result@1`; the
public active-rating DTO is `m4.3-participation-rating@1`.

## Stored data and endpoint map

| Consumer | Canonical source | Notes |
| --- | --- | --- |
| match, rounds | `artifact.match` | Stable roster team IDs remain independent of T/CT. |
| M2 match/player analytics | `artifact.analytics` | Availability and null values are preserved. |
| production match/player report | `productionReports[]` | Selected by frozen scorer version and config hash. |
| active participation rating | `activeRating` | One owner-selected H2 or H1 result; no public policy field. |
| RESCORE | `artifact` | Queues the existing scoring implementation; no `.dem` is required. |
| job status, dedup, deletion | SQLite | IDs, SHA-256, lease/job state and result binding only. |

The private `internal.recomputeSeed` contains the policy-neutral prepared
profiles required to rebuild H2 or H1. It does not contain two ratings. The
selected policy ID/digest and a source binding digest are private integrity
metadata. Public GET responses omit policy identity, prepared inputs and the
seed.

## Persistence order

For a new parse job the worker:

1. parses and validates the source in the owned child process;
2. creates M2 analytics, production reports, the prepared participation input
   and the selected active rating in memory;
3. validates `match-result@1`, gzip-compresses it and publishes immutable bytes
   through write/fsync/hard-link fencing;
4. records path, schema, SHA-256 and policy binding in SQLite;
5. verifies ownership and removes the source `.dem`, unless
   `RETAIN_SOURCE_DEMO=1` was explicitly set.

There is no durable cache, report set or participation sidecar for a new
completed match. Startup reconciliation first recovers expired leases, removes
unreferenced result publications only when no live job protects that match,
removes abandoned temporary files, and finishes source cleanup when a crash
occurred after the DB pointer but before raw deletion. The same orphan check
runs after each job. A corrupt/missing/checksum-mismatched result fails with a
typed 409; GET never reparses, backfills or returns guessed values.

## Owner-only H2/H1 procedure

`ACTIVE_RATING_POLICY` accepts only `H2` or `H1`; default is PRIMARY `H2`.
Invalid values fail startup. A server configured for a policy different from
the stored binding returns `409 REPORT_POLICY_MISMATCH` until the owner runs:

```powershell
$env:ACTIVE_RATING_POLICY = 'H1' # or H2
npm.cmd run rating:rebuild -- --dry-run
npm.cmd run rating:rebuild -- --apply
# verify the summary, then restart API/worker with the same setting
```

The CLI reads the seed from the same canonical result, validates both frozen
policy reconstructions, atomically publishes the replacement and deletes the
previous owned version only after the SQLite pointer changes. It needs neither
the `.dem`, M2 cache nor a sidecar. `?policy=...` on the HTTP endpoint is always
rejected with `422 INVALID_POLICY_SELECTOR`.

## Migration and deletion

Historical migration is explicit:

```powershell
npm.cmd run result:migrate -- --dry-run
npm.cmd run result:migrate -- --apply
```

Dry-run changes nothing. Apply creates the canonical result but deliberately
preserves every legacy raw/cache/sidecar/report file. Missing required input is
reported as `REQUIRES_ORIGINAL_DEMO` or a more specific preparation blocker;
there is no approximation and no automatic historical cleanup.

`DELETE /api/v1/matches/:id` first persists a `DELETING` intent, refuses an
active job with `409 MATCH_ACTIVE`, removes only DB-owned paths under
`DATA_DIR`, then deletes the SQLite row. Traversal and symlink components are
rejected. Re-upload after deletion creates a new match; re-upload before
deletion deduplicates by the retained SHA-256 even after raw cleanup.

## Measured storage evidence

The external inventory contained 116 `.dem` files totalling 30,474,698,491
bytes (minimum 13,139,092; median 269,609,103; p95 414,694,441; maximum
448,034,409). These are measured values, not an extrapolation.

Eight currently retained canonical test results were measured separately:

| Section | min | median | p95/max | mean |
| --- | ---: | ---: | ---: | ---: |
| gzip result | 159,471 B | 182,988 B | 293,262 B | 211,572 B |
| uncompressed JSON | 2,678,843 B | 3,029,661 B | 5,427,512 B | 3,701,318 B |
| `artifact` JSON | 847,287 B | 953,484 B | 1,641,083 B | 1,139,535 B |
| `activeRating` JSON | 71,742 B | 80,893 B | 103,275 B | 84,801 B |
| `recomputeSeed` JSON | 151,806 B | 154,504 B | 311,802 B | 209,843 B |
| production reports JSON | 1,605,647 B | 1,843,031 B | 3,370,904 B | 2,266,692 B |

Section sizes are uncompressed serialized JSON and overlap only at the
top-level container boundary. The seed is materially smaller than the full
artifact/report payload and is the minimum already-confirmed input that allows
exact H2/H1 rebuilds. No claim is made that eight results characterize every
possible demo size.

## M4.5 compatibility closure

The obsolete P2/C2+S2 rating route is no longer registered. Historical legacy
files are left untouched. The internal prepared-profile kernel and context
builder remain because the active H2/H1 result and owner rebuild use them;
M2, production reports and RESCORE continue to read the canonical result.
